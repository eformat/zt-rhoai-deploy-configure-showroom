= Module 3: Configuring the Model-Serving Platform
:navtitle: Module 3: Model-Serving Platform
:toc: macro
:toclevels: 1
:icons: font

With {rhoai-short} installed, the model-serving platform must be prepared before models can be
deployed. In this module you enable KServe single-model serving and make the pre-installed vLLM CPU
runtime available in your project. Model weights are pulled from public OCI modelcar images, so no
object storage is required — configuring an object-storage connection is shown as an optional step.

== Learning objectives

By the end of this module you will be able to:

* Enable model serving (KServe single-model serving) for projects
* Make the pre-installed vLLM CPU (x86) `ServingRuntime` available in your project
* (Optional) Create an S3/URI connection Secret with the correct connection-type annotation
* Set a default cluster-wide deployment strategy

== Prerequisites

* {rhoai-short} is `Ready` (xref:01-install-connected.adoc[Module 1] or
  xref:02-install-disconnected.adoc[Module 2] complete)
* No object storage required — model weights are pulled from public OCI modelcar images

== Exercise 1: Create the workshop project

[source,bash,role="execute",subs="attributes"]
----
oc new-project {project_name} 2>/dev/null || oc project {project_name}
oc label namespace {project_name} opendatahub.io/dashboard=true --overwrite
----

=== Verify

* `oc get project {project_name}` shows the project `Active`.

== Exercise 2: Enable model serving

Single-model serving (KServe) is enabled cluster-wide in the {rhoai-short} dashboard. In
{rhoai-short} 3.4 the multi-model (ModelMesh) platform has been removed, so the older
*Model serving platforms* checkboxes are replaced by a single *Enable model serving* toggle.

. In the {rhoai-short} dashboard, go to *Settings -> Cluster settings -> General settings*.

. Under *Model deployments*, ensure *Enable model serving* is on.

Alternatively confirm KServe is managed in the DSC:

[source,bash,role="execute"]
----
oc get datasciencecluster default-dsc -o jsonpath='{.spec.components.kserve.managementState}{"\n"}'
----

=== Verify

* The single-model serving option is available when you create a model server in a project, and the
  command above prints `Managed`.

== Exercise 3: Make a vLLM serving runtime available

{rhoai-short} {rhoai_version} ships a set of vLLM serving runtimes out of the box. On a CPU-only
cluster the relevant one is *vLLM CPU (x86) ServingRuntime for KServe* (Technology Preview) — it is
pre-installed and enabled, and it uses the Red Hat-supported, digest-pinned vLLM CPU image, so you
do not build or ship your own runtime.

You can confirm it under *Settings -> Serving runtimes* in the {rhoai-short} dashboard (toggle
*Enabled*). It is delivered as a runtime *template*: deploying a model through the dashboard
instantiates it into your project automatically. Because this workshop drives everything from the
CLI, instantiate it into the project once, up front:

[source,bash,role="execute",subs="attributes"]
----
oc process -n redhat-ods-applications vllm-cpu-x86-runtime-template \
  | oc apply -n {project_name} -f -
----

=== Verify

* The `vllm-cpu-x86-runtime` `ServingRuntime` now exists in the project:
+
[source,bash,role="execute",subs="attributes"]
----
oc get servingruntime vllm-cpu-x86-runtime -n {project_name}
----

== Exercise 4 (Optional): Create a storage connection Secret

[NOTE]
====
This workshop loads all model weights from *OCI modelcar images* (`oci://...`), so *no object
storage and no connection Secret are required* to complete it. This exercise is included only to
show how you would stage weights in S3-compatible object storage instead. Skip it if your cluster
has no S3 endpoint.
====

KServe recognises a connection by the `opendatahub.io/connection-type-protocol` annotation. If you
were serving weights from object storage, you would create an S3 (or URI) connection Secret so the
model could be auto-injected at deploy time, then point the `InferenceService` `storageUri` at an
`s3://` path instead of the `oci://` modelcar.

[source,bash,role="execute",subs="attributes"]
----
# Edit the placeholders in the template first (endpoint, bucket, keys), then apply:
oc apply -f manifests/03-serving-platform/connection-s3.yaml -n {project_name}
----

=== Verify

* The Secret carries the annotation and appears as a connection in the project:
+
[source,bash,role="execute",subs="attributes"]
----
oc get secret aws-connection-models -n {project_name} \
  -o jsonpath='{.metadata.annotations.opendatahub\.io/connection-type-protocol}{"\n"}'
----

== Exercise 5 (Optional): Set a default deployment strategy

On the same *Settings -> Cluster settings -> General settings* page, under *Default deployment
strategy*, choose a cluster-wide default for KServe deployments (*Rolling update* or *Recreate*)
to match your update-availability requirements.

== Module summary

* KServe single-model serving is enabled.
* The pre-installed `vllm-cpu-x86-runtime` `ServingRuntime` is available in `{project_name}`.
* Model weights load from OCI modelcar images; an object-storage connection is optional.
