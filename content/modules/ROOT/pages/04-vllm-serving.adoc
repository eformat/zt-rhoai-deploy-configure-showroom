= Module 4: Model Serving with vLLM
:navtitle: Module 4: Serving with vLLM
:toc: macro
:toclevels: 1
:icons: font

vLLM is the default LLM serving runtime in {rhoai} {rhoai_version}. In this module you deploy a model
on a *CPU-only* cluster and make OpenAI-compatible inference requests — no GPU required.

== Learning objectives

By the end of this module you will be able to:

* Deploy `{cpu_model}` (single-node, no scheduler) on the vLLM runtime
* Send an inference request to the OpenAI-compatible endpoint
* Expose the model on an external route
* Deploy a vLLM simulator for a GPU-free smoke test
* Read the `InferenceService` / `ServingRuntime` YAML to understand vLLM arguments

== Prerequisites

* The model-serving platform is configured (xref:03-model-serving-platform.adoc[Module 3] complete)
* A storage connection or URI for the model

== Exercise 1: Deploy the CPU model

Deploy `{cpu_model}` as an `InferenceService` bound to the vLLM runtime. The manifest requests CPU
only and disables the scheduler for single-node serving. It also carries the
`networking.kserve.io/visibility: exposed` label, so KServe creates a managed external route (the
same as ticking *Make deployed models available through an external route* in the dashboard).

[source,bash,role="execute",subs="attributes"]
----
oc apply -k manifests/04-vllm/qwen25-05b -n {project_name}
----

Wait for the model to become ready:

[source,bash,role="execute",subs="attributes"]
----
oc wait inferenceservice/qwen25-05b -n {project_name} --for=condition=Ready --timeout=15m
----

=== Verify

* The `InferenceService` reports `READY=True`:
+
[source,bash,role="execute",subs="attributes"]
----
oc get inferenceservice qwen25-05b -n {project_name}
----

== Exercise 2: Query the OpenAI-compatible API

. Because the model is exposed (Exercise 1), `.status.url` is the *external* HTTPS route, reachable
  from the bastion. Capture it and send a completion request:
+
[source,bash,role="execute",subs="attributes"]
----
URL=$(oc get inferenceservice qwen25-05b -n {project_name} -o jsonpath='{.status.url}')
# -> https://qwen25-05b-{project_name}.apps.<cluster-domain>
curl -sk $URL/v1/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"qwen25-05b","prompt":"Red Hat OpenShift AI is","max_tokens":16}'
----
+
[TIP]
====
For the *internal* (in-cluster) endpoint instead, use `.status.address.url` — it resolves to
`http://qwen25-05b-predictor.{project_name}.svc.cluster.local:8080` and only works from a pod or
in-cluster terminal, not the bastion.
====

=== Verify

* The call returns HTTP 200 with a JSON body containing generated text in `choices[0].text`.

== Exercise 3: Inspect the KServe-managed external route

By default a KServe RawDeployment `InferenceService` only creates an in-cluster (headless) Service.
The `networking.kserve.io/visibility: exposed` label on the manifest (Exercise 1) tells KServe to
also create and *own* an edge-terminated `Route` — exactly what the dashboard's *Make deployed
models available through an external route* checkbox does. You never write the `Route` yourself, and
KServe reconciles it with the `InferenceService`.

. Confirm KServe created the route and that `.status.url` points at it:
+
[source,bash,role="execute",subs="attributes"]
----
oc get route -n {project_name} -l serving.kserve.io/inferenceservice=qwen25-05b
oc get inferenceservice qwen25-05b -n {project_name} -o jsonpath='{.status.url}{"\n"}'
----

[WARNING]
====
This external route is *unauthenticated* — anyone who can reach the cluster's ingress can call the
model. That is the same warning the dashboard shows when you tick the box. It is fine for a
single-user workshop, but not for shared or production use.

*Governed* external access — API-key authentication and token rate limiting — is what
xref:05-maas-governance.adoc[Module 5] adds, by republishing the model through the *MaaS inference
gateway* (a Gateway API gateway fronted by Red Hat Connectivity Link).
====

[NOTE]
====
The cluster's `data-science-gateway` fronts the {rhoai-short} dashboard UI and OAuth login — it is
*not* an inference gateway. MaaS provisions its own `maas-default-gateway` for governed model
traffic.
====

=== Verify

* `oc get route -n {project_name}` shows a KServe-owned route for `qwen25-05b`, and `.status.url` is
  the external `https://` endpoint you queried in Exercise 2.

== Exercise 4: Deploy the vLLM simulator (GPU-free smoke test)

The vLLM simulator responds to the OpenAI API without loading real weights — useful for validating
the serving path and, later, for scaling exercises.

[source,bash,role="execute",subs="attributes"]
----
oc apply -k manifests/04-vllm/simulator -n {project_name}
oc wait inferenceservice/{sim_model} -n {project_name} --for=condition=Ready --timeout=10m
----

=== Verify

* A completion request to the simulator endpoint returns a successful response.

== Exercise 5 (Optional): Inspect the vLLM runtime arguments

[source,bash,role="execute",subs="attributes"]
----
oc get inferenceservice qwen25-05b -n {project_name} -o yaml | less
oc get servingruntime -n {project_name} -o yaml | less
----

Notice the vLLM `args` (for example `--max-model-len`, `--dtype`) and how the CPU profile omits GPU
resource requests.

== Module summary

* You served `{cpu_model}` on vLLM on a CPU-only cluster and got a 200 from `/v1/completions`.
* You reached the model over an external route.
* You deployed the simulator for GPU-free testing.
