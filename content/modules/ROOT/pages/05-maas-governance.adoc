= Module 5: Governing Access with Models-as-a-Service (MaaS)
:navtitle: Module 5: MaaS Governance
:toc: macro
:toclevels: 1
:icons: font

Serving a model is not enough for shared environments — access must be governed. {maas} adds a
subscription and rate-limit layer over model serving, backed by an API gateway
({rhcl} / Kuadrant) and a PostgreSQL-backed API-key store.

[IMPORTANT]
====
*Technology Preview.* Serving vLLM models through {maas} is a Technology Preview feature in
{rhoai} {rhoai_version}. APIs and behaviour may change; it is not supported for production use.
====

== Learning objectives

By the end of this module you will be able to:

* Enable {maas} in the `DataScienceCluster` and dashboard
* Provision the MaaS PostgreSQL database and `maas-db-config` secret
* Install {rhcl}, register Kuadrant, and bootstrap the gateway
* Install the gateway-native serving operators (Leader Worker Set, JobSet) and deploy a model as an
  `LLMInferenceService` attached to the MaaS gateway
* Publish and govern it with `MaaSModelRef`, `MaaSSubscription`, and `MaaSAuthPolicy` custom resources
* Mint an API key, call the model through the gateway, and demonstrate token rate limiting (HTTP 429)
* Enable User Workload Monitoring so served-model metrics reach the dashboard, then view vLLM engine
  metrics and MaaS per-subscription token telemetry

== Prerequisites

* xref:04-vllm-serving.adoc[Module 4] complete (KServe single-model serving working)
* Cluster-admin to enable {maas} in the `DataScienceCluster`; {rhcl} and cert-manager installable

== Exercise 1: Provision PostgreSQL and secrets

The MaaS API needs its database *before* it is enabled, or `maas-api` will crash-loop.

. Create the database credentials and connection secret:
+
[source,bash,role="execute"]
----
POSTGRES_PASSWORD=$(openssl rand -base64 16 | tr -d '=+/')
# The Red Hat rhel9/postgresql-15 image reads POSTGRESQL_* env vars (not POSTGRES_*)
# to create the user, password, and database on first start.
oc create secret generic postgres-creds -n redhat-ods-applications \
  --from-literal=POSTGRESQL_USER=maas \
  --from-literal=POSTGRESQL_PASSWORD="${POSTGRES_PASSWORD}" \
  --from-literal=POSTGRESQL_DATABASE=maas
oc create secret generic maas-db-config -n redhat-ods-applications \
  --from-literal=DB_CONNECTION_URL="postgresql://maas:${POSTGRES_PASSWORD}@postgres:5432/maas?sslmode=disable"
----

. Deploy PostgreSQL:
+
[source,bash,role="execute"]
----
oc apply -k manifests/05-maas/postgres -n redhat-ods-applications
oc rollout status deploy/postgres -n redhat-ods-applications
----

=== Verify

* The `postgres` deployment is `Available` and both secrets exist in `redhat-ods-applications`.

== Exercise 2: Install Red Hat Connectivity Link and bootstrap the gateway

The order matters here. The Kuadrant custom resource and the gateway both depend on
resources that do not exist until the operators have finished installing, so each step
below waits for its prerequisite before moving on.

. Install the {rhcl} and cert-manager operators (subscriptions only):
+
[source,bash,role="execute"]
----
oc apply -k manifests/05-maas/connectivity-link
----

. Wait for both operator CSVs to reach `Succeeded` — the Kuadrant CRD is not registered
until the {rhcl} operator install completes:
+
[source,bash,role="execute"]
----
oc wait --for=jsonpath='{.status.state}'=AtLatestKnown \
  subscription/rhcl-operator -n openshift-operators --timeout=5m
oc wait --for=jsonpath='{.status.phase}'=Succeeded \
  csv/$(oc get subscription rhcl-operator -n openshift-operators -o jsonpath='{.status.currentCSV}') \
  -n openshift-operators --timeout=5m
oc wait --for=jsonpath='{.status.state}'=AtLatestKnown \
  subscription/openshift-cert-manager-operator -n cert-manager-operator --timeout=5m
oc wait --for=jsonpath='{.status.phase}'=Succeeded \
  csv/$(oc get subscription openshift-cert-manager-operator -n cert-manager-operator -o jsonpath='{.status.currentCSV}') \
  -n cert-manager-operator --timeout=5m
----

. Register Kuadrant now that its CRD exists, and wait for it to become ready:
+
[source,bash,role="execute"]
----
oc apply -f manifests/05-maas/connectivity-link/kuadrant.yaml
oc wait --for=condition=Ready kuadrant/kuadrant -n kuadrant-system --timeout=5m
----

. Let Authorino trust the cluster service CA. When the Kuadrant CR becomes `Ready` the operator
creates the default `Authorino` instance. Its MaaS authorization calls back to `maas-api` over the
service's HTTPS port, whose certificate is signed by the OpenShift *service-serving* CA — which the
Authorino image does not trust by default. Without this, the subscription check fails TLS
verification, every request is denied, and `+/maas-api/v1/models+` comes back empty. Create the two
auto-injected CA `ConfigMaps` and mount them into Authorino's certificate directory:
+
[source,bash,role="execute"]
----
oc apply -f manifests/05-maas/connectivity-link/authorino-service-ca-trust.yaml
# Give the service-ca / network operators a moment to populate the ConfigMaps, then mount them.
oc wait --for=jsonpath='{.data.service-ca\.crt}' configmap/authorino-service-ca \
  -n kuadrant-system --timeout=2m
oc patch authorino authorino -n kuadrant-system --type=merge -p '{"spec":{"volumes":{"items":[{"name":"ca-trust","mountPath":"/etc/pki/tls/certs","configMaps":["authorino-trusted-ca-bundle","authorino-service-ca"]}]}}}'
oc rollout status deploy/authorino -n kuadrant-system --timeout=5m
----
+
[NOTE]
====
Leave Authorino's `listener` and `oidcServer` TLS *disabled* (the operator default). The Kuadrant
`ext_authz` filter talks to Authorino over plaintext gRPC on `:50051`; enabling the TLS listener
breaks that path and turns every authorized request into a `500`. This step only adds *trusted CA
material*, it does not enable a TLS listener.
====

. Create the MaaS gateway. The manifests carry a `$\{CLUSTER_DOMAIN}` placeholder, so they are
built with `oc kustomize` and rendered through `envsubst` before applying — the gateway name,
namespace, and `GatewayClass` are fixed values the MaaS controller expects and must not be changed.
+
There are two modes; pick the one that matches your cluster:
+
--
*ClusterIP + Route (default — RHDP, bare-metal, on-prem, disconnected).* These clusters have no
LoadBalancer provider, so the gateway `Service` is created as `ClusterIP` and exposed by an OpenShift
`Route` that re-encrypts to it (the same pattern the built-in `data-science-gateway` uses):

[source,bash,role="execute"]
----
export CLUSTER_DOMAIN=$(oc get ingress.config cluster -o jsonpath='{.spec.domain}')
oc kustomize manifests/05-maas/gateway/clusterip | envsubst '${CLUSTER_DOMAIN}' | oc apply -f -
oc wait --for=condition=Programmed gateway/maas-default-gateway \
  -n openshift-ingress --timeout=5m
----

*LoadBalancer (cloud — AWS/ROSA/OSD, or on-prem with MetalLB).* Only use this if your cluster has a
LoadBalancer provider; otherwise the gateway `Service` stays `<pending>` and the gateway never reaches
`Programmed=True`:

[source,bash,role="execute"]
----
export CLUSTER_DOMAIN=$(oc get ingress.config cluster -o jsonpath='{.spec.domain}')
oc kustomize manifests/05-maas/gateway/loadbalancer | envsubst '${CLUSTER_DOMAIN}' | oc apply -f -
oc wait --for=condition=Programmed gateway/maas-default-gateway \
  -n openshift-ingress --timeout=5m
----
--

=== Verify

* Both operator CSVs report `Succeeded`, `kuadrant/kuadrant` is `Ready`, and
  `gateway/maas-default-gateway` in `openshift-ingress` reports `Programmed=True`.
* In ClusterIP mode, `oc get route maas-gateway-route -n openshift-ingress` is `Admitted`
  and the `maas-gw-service-tls` secret has been provisioned by the service-ca operator.

[TIP]
====
*Enable the Connectivity Link console plugin (optional, handy for debugging).* {rhcl} ships a
`kuadrant-console-plugin` `ConsolePlugin` that is *present but not enabled* after install. Enabling
it adds a *Connectivity Link* section to the {ocp} console with an Overview dashboard — gateway
health, per-gateway traffic analysis, policies, `HTTPRoutes`, and API keys — which makes it much
easier to see why a gateway is `Unknown`/unhealthy or a policy is not `Enforced` later in this
module.

Enable it in the console: *Administration -> Cluster Settings -> Configuration -> Console
(operator.openshift.io) -> Console plugins*, then set `kuadrant-console-plugin` to *Enabled*. Or
from the CLI (appends to the existing plugin list):

[source,bash,role="execute"]
----
oc patch console.operator.openshift.io cluster --type=json \
  -p '[{"op":"add","path":"/spec/plugins/-","value":"kuadrant-console-plugin"}]'
----

The console reloads after a few seconds; the *Connectivity Link* and *Connectivity Link API
Catalog* menus then appear in the left nav.
====

== Exercise 3: Enable MaaS in the DSC and dashboard

. Enable *User Workload Monitoring* (UWM). The {rhoai-short} operator creates `ServiceMonitor` /
  `PodMonitor` resources next to each served model; UWM is the platform component that scrapes them
  and federates the metrics into the cluster Thanos Querier
  (`thanos-querier.openshift-monitoring`) that the dashboard's default *Cluster Prometheus*
  datasource reads. Without it the *Observe & monitor* dashboard renders but every model panel
  stays empty, and there is nothing for the {maas} token-usage or the Module 6 KEDA autoscaler to
  read. Enable it first so the stack is up by the time a model is serving:
+
[source,bash,role="execute"]
----
oc apply -k manifests/05-maas/uwm
----
+
Wait for the user-workload monitoring stack to come up (the StatefulSet is created a few seconds
after the ConfigMap is applied):
+
[source,bash,role="execute"]
----
until oc get statefulset prometheus-user-workload -n openshift-user-workload-monitoring >/dev/null 2>&1; do
  echo "waiting for the user-workload monitoring stack to be created..."; sleep 5
done
oc rollout status statefulset/prometheus-user-workload -n openshift-user-workload-monitoring --timeout=5m
----

. Install the serving-path operators the `LLMInferenceService` depends on — *Leader Worker Set*
  and *JobSet* — *before* enabling MaaS in the DSC. KServe uses these to run the gateway-native
  serving pods, and enabling MaaS while they are missing makes the `DataScienceCluster` report a
  `LeaderWorkerSet not installed` warning. (They are also the llm-d prerequisites reused in
  xref:06-llmd-scaling.adoc[Module 6].) The manifest creates only namespaces, operator groups, and
  subscriptions, so it is safe to apply in one go:
+
[source,bash,role="execute"]
----
oc apply -k manifests/05-maas/serving-operators
----

. Wait for both operator CSVs to reach `Succeeded` — their activation CRDs are not registered
  until the installs complete:
+
[source,bash,role="execute"]
----
oc wait --for=jsonpath='{.status.state}'=AtLatestKnown \
  subscription/leader-worker-set -n openshift-lws-operator --timeout=5m
oc wait --for=jsonpath='{.status.phase}'=Succeeded \
  csv/$(oc get subscription leader-worker-set -n openshift-lws-operator -o jsonpath='{.status.currentCSV}') \
  -n openshift-lws-operator --timeout=5m
oc wait --for=jsonpath='{.status.state}'=AtLatestKnown \
  subscription/job-set -n openshift-jobset-operator --timeout=5m
oc wait --for=jsonpath='{.status.phase}'=Succeeded \
  csv/$(oc get subscription job-set -n openshift-jobset-operator -o jsonpath='{.status.currentCSV}') \
  -n openshift-jobset-operator --timeout=5m
----

. Activate both operators by creating their singleton `cluster` CRs. The
  `LeaderWorkerSetOperator` / `JobSetOperator` CRDs exist only after the CSVs above are
  `Succeeded`, which is why they are applied separately from the subscriptions:
+
[source,bash,role="execute"]
----
oc apply -f manifests/05-maas/serving-operators/operator-config.yaml
----

. Install the observability backend operators — *Cluster Observability Operator* (COO) and
  *Red Hat build of OpenTelemetry*. These provide the Perses / `MonitoringStack` backend behind
  the dashboard's *Observe & monitor -> Dashboard* tab; without them the tab loads but reports
  *Service Unavailable*:
+
[source,bash,role="execute"]
----
oc apply -k manifests/05-maas/observability-operators
----

. Wait for both operator CSVs to reach `Succeeded`:
+
[source,bash,role="execute"]
----
oc wait --for=jsonpath='{.status.state}'=AtLatestKnown \
  subscription/cluster-observability-operator -n openshift-cluster-observability-operator --timeout=5m
oc wait --for=jsonpath='{.status.phase}'=Succeeded \
  csv/$(oc get subscription cluster-observability-operator -n openshift-cluster-observability-operator -o jsonpath='{.status.currentCSV}') \
  -n openshift-cluster-observability-operator --timeout=5m
oc wait --for=jsonpath='{.status.state}'=AtLatestKnown \
  subscription/opentelemetry-product -n openshift-opentelemetry-operator --timeout=5m
oc wait --for=jsonpath='{.status.phase}'=Succeeded \
  csv/$(oc get subscription opentelemetry-product -n openshift-opentelemetry-operator -o jsonpath='{.status.currentCSV}') \
  -n openshift-opentelemetry-operator --timeout=5m
----
+
Once COO is installed (and DSCI monitoring is already `Managed` from the base install), the
{rhoai-short} operator builds the `data-science-monitoringstack` (Prometheus + Thanos) and the
`data-science-perses` instance in `redhat-ods-monitoring`. Wait for the monitoring `ConfigMap`
that the next step depends on to appear:
+
[source,bash,role="execute"]
----
until oc get configmap prometheus-web-tls-ca -n redhat-ods-monitoring >/dev/null 2>&1; do
  echo "waiting for the RHOAI operator to build the MonitoringStack..."; sleep 10
done
----

. Apply two small workarounds for a known {rhoai} {rhoai_version} + COO version gap (see the note
  below), then restart Prometheus so it remounts the new secret:
+
[source,bash,role="execute"]
----
# 1) The default Perses "Cluster Prometheus" datasource the dashboard panels resolve to.
oc apply -k manifests/05-maas/observability-datasource

# 2) Mirror the service-ca bundle into a Secret of the same name (the COO MonitoringStack
#    references prometheus-web-tls-ca as a Secret; RHOAI creates it as a ConfigMap).
oc create secret generic prometheus-web-tls-ca -n redhat-ods-monitoring \
  --from-literal=service-ca.crt="$(oc get cm prometheus-web-tls-ca -n redhat-ods-monitoring -o jsonpath='{.data.service-ca\.crt}')" \
  --dry-run=client -o yaml | oc apply -f -

# 3) Force Prometheus to remount the secret, then wait for the stack to go Available.
oc delete pod -l app.kubernetes.io/name=prometheus -n redhat-ods-monitoring --ignore-not-found
oc wait --for=condition=Available monitoringstack/data-science-monitoringstack \
  -n redhat-ods-monitoring --timeout=10m
----
+
[NOTE]
====
*Why these workarounds?* {rhoai} {rhoai_version} was built against an older Cluster Observability
Operator than the one currently in the catalog (COO 1.5.1), and two of the resources the RHOAI
Monitoring controller generates no longer pass the newer CRD/stack validation:

* The controller's `PersesDatasource` (`cluster-prometheus-datasource`, the *default* datasource
  every panel resolves to) omits `caCert.namespace`, which COO 1.5.1 now requires — so the apply
  fails and the datasource is never created. Panels then error with
  `No datasource found for kind 'PrometheusDatasource' and name 'undefined'`. The manifest
  re-creates it (plus its `ServiceAccount`, RBAC, and token secret) with the required field; the
  operator then adopts it and `Monitoring` reports `Ready=True`.
* RHOAI creates `prometheus-web-tls-ca` as a `ConfigMap`, but the COO 1.5.1 `MonitoringStack`
  references it as a `Secret`, leaving the Prometheus pod stuck in `Init`. Mirroring the CA into a
  like-named `Secret` (both can coexist) unblocks it.

Both steps become unnecessary once RHOAI ships a build aligned with COO 1.5.x.
====

. Enable MaaS in the `DataScienceCluster` and the dashboard:
+
[source,bash,role="execute"]
----
oc patch datasciencecluster default-dsc --type merge \
  --patch-file manifests/05-maas/enable/dsc-maas-patch.yaml
oc patch odhdashboardconfig odh-dashboard-config -n redhat-ods-applications --type merge \
  --patch-file manifests/05-maas/enable/dashboard-maas-patch.yaml
----
+
This sets `spec.components.kserve.modelsAsService.managementState: Managed` in the
`DataScienceCluster`, and turns on the `modelAsService` and `observabilityDashboard` dashboard
feature flags in `OdhDashboardConfig`.

. Restart the dashboard so it picks up the new feature flags and the now-available MaaS backend.
  The dashboard pods were started before MaaS was enabled, so without this the *Models as a
  Service* view and the *Observe & monitor* nav do not appear:
+
[source,bash,role="execute"]
----
oc rollout restart deploy/rhods-dashboard -n redhat-ods-applications
oc rollout status deploy/rhods-dashboard -n redhat-ods-applications --timeout=3m
----

=== Verify

* `oc get monitoring default-monitoring -o jsonpath='{.status.conditions[?(@.type=="Ready")].status}'`
  reports `True`, and `oc get monitoringstack data-science-monitoringstack -n redhat-ods-monitoring`
  is `Available` with its Prometheus pod `3/3 Running`.
* After a browser refresh, the {rhoai-short} dashboard shows the *Models as a Service* view (AI
  asset endpoints, API keys) and an *Observe & monitor -> Dashboard (Tech Preview)* nav item.
* On the *Observe & monitor -> Dashboard*, the *Cluster* tab renders live data (System health,
  Memory/CPU utilization, Inbound traffic) instead of
  `No datasource found ... name 'undefined'`. The *GPU utilization*, *Deployed models*, and
  *Request success rate* panels show *No data* until a model is served and called (this is a
  CPU-only cluster with no GPUs; the model panels populate after Exercises 4-7).

== Exercise 5: Publish and govern the model

Publish the `LLMInferenceService` through MaaS and govern it with a subscription and a token rate
limit.

. Apply the governance CRs:
+
[source,bash,role="execute",subs="attributes"]
----
oc apply -k manifests/05-maas/subscription
----
+
This creates a `MaaSModelRef` (pointing at the `qwen25-05b-maas` `LLMInferenceService`), a
`MaaSSubscription` (`qwen25-05b-demo`, with a 100-token-per-minute rate limit granted to all
authenticated users), and a `MaaSAuthPolicy`.
+
[NOTE]
====
Each manifest pins its own namespace, so the command has *no* `-n` flag. The `MaaSModelRef` lands
in the workshop project (`{project_name}`, where the `LLMInferenceService` lives), while the
`MaaSSubscription` and `MaaSAuthPolicy` land in `models-as-a-service` — the only namespace
`maas-api` reads subscriptions from (its `MAAS_SUBSCRIPTION_NAMESPACE`). A subscription applied
anywhere else is silently ignored and `/maas-api/v1/models` returns an empty catalog. Both grant
access to the `system:authenticated:oauth` group — the group the OpenShift OAuth/OIDC identity
actually presents; plain `system:authenticated` never matches and every call is denied (403).
====

. Wire up per-subscription telemetry so gateway token usage is broken out by subscription. Both
  CRs target `maas-default-gateway` and build on the `MaaSAuthPolicy` you just created, so they are
  applied after governance. You *view* these metrics in Exercise 8, after generating traffic:
+
[source,bash,role="execute"]
----
oc apply -k manifests/05-maas/telemetry
----
+
This creates an Istio `Telemetry` (tagging gateway latency with the `x-maas-subscription` header)
and a Kuadrant `TelemetryPolicy` (labelling token-usage metrics with the model, user, subscription,
organization, and cost center from the authenticated request).

[NOTE]
====
The singleton `Tenant` (`default-tenant`) is bootstrapped automatically by the `maas-controller`
once MaaS is Managed and {rhcl} is installed — the workshop does not create one. If the controller
is crash-looping, it is almost always waiting on the Kuadrant `TokenRateLimitPolicy` CRD from
Exercise 2; confirm that step completed.
====

=== Verify

* `oc get maasmodelref,maassubscription,maasauthpolicy -n {project_name}` shows all three, and the
  model appears in the *Models as a Service* view in the dashboard.
* `oc get telemetry,telemetrypolicy -n openshift-ingress` lists `latency-per-subscription` and
  `maas-telemetry`.

== Exercise 6: Mint an API key and call the model

MaaS issues API keys through the `maas-api` endpoint, not as a Kubernetes Secret. Authenticate with
your OpenShift token to mint a key bound to the subscription, then call the model through the
gateway.

. Resolve the gateway host and mint an API key (returned only once):
+
[source,bash,role="execute"]
----
export CLUSTER_DOMAIN=$(oc get ingresses.config.openshift.io cluster -o jsonpath='{.spec.domain}')
export HOST="https://maas.${CLUSTER_DOMAIN}"
export API_KEY=$(curl -sSk -X POST "${HOST}/maas-api/v1/api-keys" \
  -H "Authorization: Bearer $(oc whoami -t)" \
  -H "Content-Type: application/json" \
  -d '{"name":"workshop-key","expiresIn":"1h","subscription":"qwen25-05b-demo"}' | jq -r .key)
echo "API key: ${API_KEY:0:12}..."
----

. Discover the published model id and call the OpenAI-compatible chat endpoint:
+
[source,bash,role="execute"]
----
MODEL_JSON=$(curl -sSk "${HOST}/maas-api/v1/models" -H "Authorization: Bearer ${API_KEY}")
export MODEL_NAME=$(echo "$MODEL_JSON" | jq -re '[.data[] | select(.ready==true)][0].id')
# The catalog also returns each model's gateway path (/<namespace>/<LLMInferenceService>). Chat
# requests go to that path, NOT the bare /v1/chat/completions — the gateway routes by prefix and
# a bare path 404s.
export MODEL_PATH=$(echo "$MODEL_JSON" | jq -re '[.data[] | select(.ready==true)][0].url' | sed -E 's#^https?://[^/]+##')
echo "Model: $MODEL_NAME  ->  ${HOST}${MODEL_PATH}"
curl -sSk "${HOST}${MODEL_PATH}/v1/chat/completions" \
  -H "Authorization: Bearer ${API_KEY}" \
  -H "Content-Type: application/json" \
  -d "{\"model\":\"${MODEL_NAME}\",\"messages\":[{\"role\":\"user\",\"content\":\"Hello\"}],\"max_tokens\":50}" | jq .
----

=== Verify

* The chat request returns *HTTP 200* with a completion. A request with no `Authorization` header
  returns *HTTP 401*.

== Exercise 7: Demonstrate rate limiting

Send requests beyond the subscription's token limit and observe throttling. This reuses the
`$HOST`, `$API_KEY`, `$MODEL_NAME`, and `$MODEL_PATH` variables exported in the previous step.

[source,bash,role="execute"]
----
for i in $(seq 1 16); do
  curl -sSk -o /dev/null -w "%{http_code}\n" "${HOST}${MODEL_PATH}/v1/chat/completions" \
    -H "Authorization: Bearer ${API_KEY}" -H "Content-Type: application/json" \
    -d "{\"model\":\"${MODEL_NAME}\",\"messages\":[{\"role\":\"user\",\"content\":\"hi\"}],\"max_tokens\":32}"
done | sort | uniq -c
----

=== Verify

* Requests exceeding the subscription limit return *HTTP 429*.

== Exercise 8: View engine metrics and MaaS telemetry

The traffic from Exercises 6 and 7 has produced metrics. Because User Workload Monitoring was
enabled in Exercise 3, the served model's `kserve_vllm` series are now in the cluster Thanos and
the {maas} gateway's token usage is broken out per subscription.

. View *vLLM engine throughput*. In the {ocp} console, go to *Observe -> Metrics* and run these
  queries. The workshop drives the model in short manual bursts, so an instantaneous `rate(...)`
  reads 0 most of the time; a windowed `increase(...)` captures the tokens the engine actually
  processed over the last 15 minutes:
+
[source,promql]
----
sum(increase(kserve_vllm:prompt_tokens_total[15m]))
----
+
[source,promql]
----
sum(increase(kserve_vllm:generation_tokens_total[15m]))
----
+
[source,promql]
----
kserve_vllm:kv_cache_usage_perc
----
+
NOTE: These are PromQL expressions — paste them into the *Observe -> Metrics* query box in the
console ({metrics_console_url}), not the terminal. `prompt_tokens` are the input tokens the engine
read; `generation_tokens` are the output tokens it produced. `kv_cache_usage_perc` is the KV-cache
gauge (the older `gpu_cache_usage_perc` name is gone in this vLLM build); it sits near 0 on a
lightly loaded CPU model and rises under concurrent load. Queue depth
(`kserve_vllm:num_requests_waiting`) only builds under concurrent traffic, so it stays 0 here — you
drive it up and scale on it in xref:06-llmd-scaling.adoc[Module 6].

. View *MaaS per-subscription telemetry* — the metrics that map directly to the subscription's
  token rate limit (100 tokens / 1 minute). These come from Limitador (the {maas} rate limiter),
  labeled per subscription by the `TelemetryPolicy` from Exercise 5, so unlike the engine metrics
  above they are broken out by `subscription`:
+
[source,promql]
----
authorized_hits{subscription="qwen25-05b-demo"}
----
+
[source,promql]
----
increase(authorized_hits{subscription="qwen25-05b-demo"}[1m])
----
+
[source,promql]
----
limited_calls{subscription="qwen25-05b-demo"}
----
+
`authorized_hits` is the running total of tokens metered against the subscription — this is the
counter the limit is enforced on, so it is the engine's token counts seen from the governance side.
`increase(authorized_hits[...][1m])` is tokens consumed in the last minute, the exact 1-minute
window the `limit: 100 / window: 1m` rule measures — watch it approach 100 as you send traffic.
`limited_calls` is the number of requests rejected with HTTP 429 once that window was exhausted,
which is what you triggered in Exercise 7.

. View the same telemetry in the dashboard. In the {rhoai-short} dashboard, open *Observe &
  monitor -> Dashboard*; the token-usage panels break the `authorized_hits` counter out by
  subscription. If the dashboard shows only aggregate usage, confirm the Istio `Telemetry` and
  Kuadrant `TelemetryPolicy` from Exercise 5 exist:
+
[source,bash,role="execute"]
----
oc get telemetry,telemetrypolicy -n openshift-ingress
----

model. The `qwen25-05b` model was already published as an AI asset endpoint back in Module 4 (the
`opendatahub.io/genai-asset` label on its `InferenceService`), so once the playground is enabled the

. Enable the Llama Stack backend and reveal the *Gen AI studio* in the dashboard. The first patch

[source,bash,role="execute"]

oc patch datasciencecluster default-dsc --type merge \
