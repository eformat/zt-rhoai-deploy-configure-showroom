= Module 6: Scaling Distributed Inference (llm-d + KEDA)
:navtitle: Module 6: Scaling llm-d
:toc: macro
:toclevels: 1
:icons: font

Single-replica serving does not scale to real traffic. {rhoai} {rhoai_version} runs distributed
inference with *llm-d*, and this module scales it automatically with the *Custom Metrics
Autoscaler* (KEDA) — adding replicas from an inference signal (queue depth) rather than generic
CPU/memory, and without requiring a GPU.

[NOTE]
====
*Two autoscalers, one goal.* On GPU clusters {rhoai} {rhoai_version} offers the *Workload Variant
Autoscaler (WVA)*, which scales llm-d from KV-cache and queue signals and internally creates a KEDA
`ScaledObject` for you. This CPU-only workshop drives that same KEDA layer directly. WVA is covered
as GPU reference in <<Exercise 5 (Reference): Workload Variant Autoscaler on GPU>>.
====

== Learning objectives

By the end of this module you will be able to:

* Install the Custom Metrics Autoscaler (the llm-d serving operators come from Module 5)
* Deploy a model as an `LLMInferenceService`
* Authorize KEDA to read inference metrics from user-workload monitoring
* Scale the deployment with a KEDA `ScaledObject` driven by vLLM queue depth
* Drive load and observe a replica change
* Understand how the Workload Variant Autoscaler provides the same capability on GPU

== Prerequisites

* The model-serving platform is enabled (xref:03-model-serving-platform.adoc[Module 3])
* User Workload Monitoring enabled, so vLLM metrics reach Thanos
  (xref:07-observability.adoc[Module 7]) — KEDA scales on those metrics

== Exercise 1: Install the Custom Metrics Autoscaler

The gateway-native serving operators this module's `LLMInferenceService` needs — *Leader Worker
Set* and *JobSet* — were installed in xref:05-maas-governance.adoc[Module 5]. If you skipped
Module 5, apply them now with `oc apply -k manifests/05-maas/serving-operators` followed by
`oc apply -f manifests/05-maas/serving-operators/operator-config.yaml` (see Module 5, Exercise 4).

Here you add the *Custom Metrics Autoscaler* (KEDA). The manifest creates only a namespace,
operator group, and subscription.

. Apply the subscription:
+
[source,bash,role="execute"]
----
oc apply -k manifests/06-llmd/operators
----

. Wait for the operator CSV to reach `Succeeded`:
+
[source,bash,role="execute"]
----
oc wait --for=jsonpath='{.status.phase}'=Succeeded \
  csv -l operators.coreos.com/openshift-custom-metrics-autoscaler-operator.openshift-keda= \
  -n openshift-keda --timeout=5m
----

. Activate KEDA by creating the `KedaController` (its CRD exists only after the CSV above is
`Succeeded`, which is why it is applied separately from the subscription):
+
[source,bash,role="execute"]
----
oc apply -f manifests/06-llmd/operators/kedacontroller.yaml
oc rollout status deploy/keda-operator -n openshift-keda --timeout=5m
----

=== Verify

* The KEDA CSV reports `Succeeded` and the KEDA controller and metrics-apiserver pods are
  `Running`:
+
[source,bash,role="execute"]
----
oc get csv -n openshift-keda | grep -Ei 'custom-metrics'
oc get pods -n openshift-keda
----

== Exercise 2: Deploy an LLMInferenceService

Deploy the CPU model as an `LLMInferenceService`, which brings up the llm-d Endpoint Picker (EPP)
and vLLM pods. The manifest carries `prometheus.io/scrape` annotations so user-workload monitoring
collects the queue-depth metric KEDA scales on.

[source,bash,role="execute",subs="attributes"]
----
oc apply -k manifests/06-llmd/service -n {project_name}
oc get pods -n {project_name} -w
----

=== Verify

* The llm-d Endpoint Picker (EPP) pod and vLLM pod(s) are `Running`:
+
[source,bash,role="execute",subs="attributes"]
----
oc get pods -n {project_name} -l app.kubernetes.io/part-of=llm-d
----

* Note the Deployment name KServe created — the autoscaler targets it in the next exercise
  (expected: `qwen25-05b-llmd-kserve`):
+
[source,bash,role="execute",subs="attributes"]
----
oc get deploy -n {project_name} -l app.kubernetes.io/part-of=llm-d
----

== Exercise 3: Autoscale with KEDA

Grant KEDA read access to user-workload monitoring, then create a `ScaledObject` that scales the
vLLM Deployment on queue depth (`vllm:num_requests_waiting`) pulled from Thanos.

[source,bash,role="execute"]
----
oc apply -k manifests/06-llmd/autoscaling-keda
----

This creates, in one apply:

* a `keda-metrics-reader` ServiceAccount (bound to `cluster-monitoring-view`) and a token Secret,
  in `openshift-keda`;
* a `ClusterTriggerAuthentication` (`ai-inference-keda-thanos`) that hands that token to KEDA; and
* a `ScaledObject` (`qwen25-05b-llmd-keda`) targeting the `qwen25-05b-llmd-kserve` Deployment,
  `minReplicaCount: 1`, `maxReplicaCount: 4`.

[NOTE]
====
The `ScaledObject` targets the Deployment named `qwen25-05b-llmd-kserve`. If Exercise 2 reported a
different name for your build, edit `manifests/06-llmd/autoscaling-keda/scaledobject.yaml`
(`spec.scaleTargetRef.name`) before applying.
====

=== Verify

* The `ScaledObject` reports `READY=True` and creates an underlying HPA:
+
[source,bash,role="execute",subs="attributes"]
----
oc get scaledobject -n {project_name}
oc get hpa -n {project_name}
----

== Exercise 4: Drive load and observe scaling

. Generate load against the model to build queue depth:
+
[source,bash,role="execute",subs="attributes"]
----
for i in $(seq 1 500); do
  curl -sk -o /dev/null {model_endpoint_url}/v1/completions \
    -H "Content-Type: application/json" \
    -d '{"model":"qwen25-05b","prompt":"scale test","max_tokens":64}' &
done; wait
----

. Watch the replica count climb as the queue-depth threshold is exceeded, then settle back after
  the cooldown period:
+
[source,bash,role="execute",subs="attributes"]
----
oc get deploy qwen25-05b-llmd-kserve -n {project_name} -w
----

=== Verify

* The replica count increases under load (up to `maxReplicaCount`) and scales back down once the
  queue drains.

== Exercise 5 (Reference): Workload Variant Autoscaler on GPU

On a GPU-enabled {rhoai} {rhoai_version} cluster, the *Workload Variant Autoscaler (WVA)* is the
recommended way to scale llm-d. It reads KV-cache utilization and queue depth and creates a KEDA
`ScaledObject` for you — the same engine you drove directly in Exercises 3–4.

WVA is *not runnable on this CPU build*: the `DataScienceCluster` here has no `spec.components.wva`
field, so the `VariantAutoscaling` CRD is never registered, and WVA targets accelerated hardware.
The manifests are kept as GPU guidance:

* `manifests/06-llmd/autoscaling/dsc-wva-patch.yaml` — enables WVA in the `DataScienceCluster`
  (`spec.components.wva.managementState: Managed`).
* `manifests/06-llmd/autoscaling/variantautoscaling.yaml` — a `VariantAutoscaling` CR, and (in
  comments) the preferred `LLMInferenceService.spec.scaling.wva.keda` form with a GPU
  `vllm-cuda-rhel9` image and an accelerator label.

On such a cluster the flow would be: enable WVA in the DSC → deploy the `LLMInferenceService` with
`spec.scaling.wva` (or apply a `VariantAutoscaling` CR) → WVA creates the `ScaledObject`
automatically. No `ScaledObject`, RBAC, or `ClusterTriggerAuthentication` are authored by hand.

== Module summary

* You installed the llm-d prerequisites and the Custom Metrics Autoscaler, and deployed an
  `LLMInferenceService`.
* You authorized KEDA against user-workload monitoring and scaled the deployment with a
  `ScaledObject` driven by vLLM queue depth — no GPU required.
* You drove load, watched replicas scale, and saw how the Workload Variant Autoscaler delivers the
  same capability on GPU.
