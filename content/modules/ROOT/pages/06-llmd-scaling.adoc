= Module 6: Scaling Distributed Inference (llm-d + KEDA)
:navtitle: Module 6: Scaling llm-d
:toc: macro
:toclevels: 1
:icons: font

Single-replica serving does not scale to real traffic. {rhoai} {rhoai_version} runs distributed
inference with *llm-d*, and this module scales it automatically with the *Custom Metrics
Autoscaler* (KEDA) — adding replicas from an inference signal (queue depth) rather than generic
CPU/memory, and without requiring a GPU. The model is published through the *MaaS gateway* from
xref:05-maas-governance.adoc[Module 5], so the scaling traffic is governed and its token usage
lands in the same per-subscription telemetry — the autoscaler comes with observability for free.

[NOTE]
====
*Two autoscalers, one goal.* On GPU clusters {rhoai} {rhoai_version} offers the *Workload Variant
Autoscaler (WVA)*, which scales llm-d from KV-cache and queue signals and internally creates a KEDA
`ScaledObject` for you. This CPU-only workshop drives that same KEDA layer directly. WVA is covered
as GPU reference in <<Exercise 6 (Reference): Workload Variant Autoscaler on GPU>>.
====

== Learning objectives

By the end of this module you will be able to:

* Install the Custom Metrics Autoscaler (the llm-d serving operators come from Module 5)
* Deploy a model as an `LLMInferenceService` attached to the MaaS gateway
* Publish it through MaaS with a dedicated high-limit subscription for load testing
* Authorize KEDA to read inference metrics from user-workload monitoring
* Scale the deployment with a KEDA `ScaledObject` driven by vLLM queue depth
* Drive load through the MaaS gateway and observe a replica change, correlating it with the queue
  and KV-cache metrics — and the per-subscription token telemetry — that drove it
* Understand how the Workload Variant Autoscaler provides the same capability on GPU

== Prerequisites

* The model-serving platform is enabled (xref:03-model-serving-platform.adoc[Module 3])
* {maas} enabled with the gateway running (xref:05-maas-governance.adoc[Module 5]) — this module's
  `LLMInferenceService` attaches to `maas-default-gateway` rather than a dedicated inference
  gateway, so its traffic is governed and metered like every other MaaS model
* User Workload Monitoring enabled, so vLLM metrics reach Thanos
  (xref:05-maas-governance.adoc[Module 5, Exercise 3]) — KEDA scales on those metrics

== Exercise 1: Install the Custom Metrics Autoscaler

The gateway-native serving operators this module's `LLMInferenceService` needs — *Leader Worker
Set* and *JobSet* — were installed in xref:05-maas-governance.adoc[Module 5]. If you skipped
Module 5, apply them now with `oc apply -k manifests/05-maas/serving-operators` followed by
`oc apply -f manifests/05-maas/serving-operators/operator-config.yaml` (see Module 5, Exercise 4).

Here you add the *Custom Metrics Autoscaler* (KEDA). The manifest creates only a namespace,
operator group, and subscription.

. Apply the subscription:
+
[source,bash,role="execute"]
----
oc apply -k manifests/06-llmd/operators
----

. Wait for the operator CSV to reach `Succeeded`:
+
[source,bash,role="execute"]
----
oc wait --for=jsonpath='{.status.phase}'=Succeeded \
  csv -l operators.coreos.com/openshift-custom-metrics-autoscaler-operator.openshift-keda= \
  -n openshift-keda --timeout=5m
----

. Activate KEDA by creating the `KedaController` (its CRD exists only after the CSV above is
`Succeeded`, which is why it is applied separately from the subscription):
+
[source,bash,role="execute"]
----
oc apply -f manifests/06-llmd/operators/kedacontroller.yaml
oc rollout status deploy/keda-operator -n openshift-keda --timeout=5m
----

=== Verify

* The KEDA CSV reports `Succeeded` and the KEDA controller and metrics-apiserver pods are
  `Running`:
+
[source,bash,role="execute"]
----
oc get csv -n openshift-keda | grep -Ei 'custom-metrics'
oc get pods -n openshift-keda
----

== Exercise 2: Deploy an LLMInferenceService

Deploy the CPU model as an `LLMInferenceService`, which brings up the llm-d Endpoint Picker (EPP)
and vLLM pods. The manifest carries `prometheus.io/scrape` annotations so user-workload monitoring
collects the queue-depth metric KEDA scales on.

The service's `router` attaches to the *existing* `maas-default-gateway` from Module 5
(`scheduler: {}` brings up the EPP and InferencePool, `route: {}` creates the HTTPRoute, and
`gateway.refs` binds it to that gateway) rather than standing up a dedicated `openshift-ai-inference`
gateway. This reuses one Envoy proxy — saving CPU on a single node — and puts the model under MaaS
governance, so you publish it with a subscription in Exercise 3 and its token usage flows into the
Module 5 telemetry.

[source,bash,role="execute",subs="attributes"]
----
oc apply -k manifests/06-llmd/service -n {project_name}
oc get pods -n {project_name} -w
----

=== Verify

* The llm-d Endpoint Picker (EPP) pod and vLLM pod(s) are `Running`:
+
[source,bash,role="execute",subs="attributes"]
----
oc get pods -n {project_name} -l app.kubernetes.io/name=qwen25-05b-llmd
----

* The `LLMInferenceService` reaches `Ready=True` — its HTTPRoute is accepted by
  `maas-default-gateway` (a `WaitingForGateway` status here means the router is not attached to a
  running gateway; confirm Module 5's gateway is `Programmed`):
+
[source,bash,role="execute",subs="attributes"]
----
oc wait --for=condition=Ready llminferenceservice/qwen25-05b-llmd -n {project_name} --timeout=15m
oc get llminferenceservice qwen25-05b-llmd -n {project_name}
----

* Note the Deployment name KServe created — the autoscaler targets it in Exercise 4
  (expected: `qwen25-05b-llmd-kserve`). The selector below narrows to this model's vLLM *workload*
  Deployment; the broader `app.kubernetes.io/part-of=llminferenceservice` label would also match the
  router-scheduler (EPP) Deployment and any other `LLMInferenceService` in the project (such as
  Module 5's `qwen25-05b-maas`):
+
[source,bash,role="execute",subs="attributes"]
----
oc get deploy -n {project_name} -l app.kubernetes.io/name=qwen25-05b-llmd,kserve.io/component=workload
----
+
[NOTE]
====
*The `LLMInferenceService` deliberately omits `spec.replicas`* so the KEDA `ScaledObject` in
Exercise 4 can own the replica count. KServe's llm-d controller only yields the workload Deployment's
replica count to an external autoscaler when `spec.replicas` is unset; the apiserver then defaults the
Deployment to `1` on create, and KEDA scales from there. If you *set* `spec.replicas`, the controller
rewrites the count on every reconcile and fights KEDA — newly added pods go `Terminating` and the
count snaps back to your fixed value (queue depth builds but replicas never hold). *Do not add
`spec.replicas` to this manifest.* The GPU-only `spec.scaling.wva` form (<<Exercise 6 (Reference):
Workload Variant Autoscaler on GPU>>) is the mutually-exclusive alternative.
====

== Exercise 3: Publish the scaling model through MaaS

The model now serves behind the MaaS gateway, which *default-denies* — every request needs an API
key bound to a subscription, or it is rejected before it can reach the queue. Publish the model and
grant it a budget so the load test in Exercise 5 can build queue depth freely.

. Apply the MaaS governance CRs for the llm-d model:
+
[source,bash,role="execute"]
----
oc apply -k manifests/06-llmd/maas-subscription
----
+
This creates a `MaaSModelRef` (pointing at the `qwen25-05b-llmd` `LLMInferenceService`), a
`MaaSSubscription` (`qwen25-05b-llmd-demo`), and a `MaaSAuthPolicy`. As in Module 5, the
`MaaSModelRef` lands in the workshop project while the subscription and auth policy land in
`models-as-a-service` (the only namespace `maas-api` reads subscriptions from), and both grant the
`system:authenticated:oauth` group.

[NOTE]
====
*Why a separate, high-limit subscription?* Module 5's `qwen25-05b-demo` subscription is capped at
100 tokens / 1 minute to *demonstrate* rate limiting (HTTP 429). That cap would throttle this load
test before a request queue could form. `qwen25-05b-llmd-demo` grants an effectively unlimited
budget (5,000,000 tokens / 1 minute) so the load generator builds `num_requests_waiting` for KEDA
to scale on *without* being throttled — while Limitador still meters it, so the token telemetry
stays populated. Module 5's rate-limit demo is left untouched.
====

=== Verify

* All three MaaS custom resources are `Active`/`Ready`, and the model's gateway endpoint is
  published:
+
[source,bash,role="execute",subs="attributes"]
----
oc get maasmodelref qwen25-05b-llmd -n {project_name}
# Query both kinds in one command with the type/name form; a bare
# `oc get maassubscription NAME1 NAME2` would treat every argument as a MaaSSubscription name.
oc get maassubscription/qwen25-05b-llmd-demo maasauthpolicy/qwen25-05b-llmd-auth -n models-as-a-service
----

== Exercise 4: Autoscale with KEDA

Grant KEDA read access to user-workload monitoring, then create a `ScaledObject` that scales the
vLLM Deployment on queue depth (`vllm:num_requests_waiting`) pulled from Thanos.

[source,bash,role="execute"]
----
oc apply -k manifests/06-llmd/autoscaling-keda
----

This creates, in one apply:

* a `keda-metrics-reader` ServiceAccount (bound to `cluster-monitoring-view`) and a token Secret,
  in `openshift-keda`;
* a `ClusterTriggerAuthentication` (`ai-inference-keda-thanos`) that hands that token to KEDA; and
* a `ScaledObject` (`qwen25-05b-llmd-keda`) targeting the `qwen25-05b-llmd-kserve` Deployment,
  `minReplicaCount: 1`, `maxReplicaCount: 4`.

[NOTE]
====
The `ScaledObject` targets the Deployment named `qwen25-05b-llmd-kserve`. If Exercise 2 reported a
different name for your build, edit `manifests/06-llmd/autoscaling-keda/scaledobject.yaml`
(`spec.scaleTargetRef.name`) before applying.
====

=== Verify

* The `ScaledObject` reports `READY=True` and creates an underlying HPA:
+
[source,bash,role="execute",subs="attributes"]
----
oc get scaledobject -n {project_name}
oc get hpa -n {project_name}
----
+
[NOTE]
====
*Give the HPA a minute to populate.* The `ScaledObject` becomes `READY=True` almost immediately, but
the HPA it creates first shows `TARGETS` as `<unknown>/5` and `REPLICAS 0` — KEDA's metrics adapter
has not yet fetched the queue-depth metric from Thanos. Within ~30–60 seconds it reports a numeric
target (`0/5` on an idle model) and applies `minReplicaCount`, so `REPLICAS` becomes `1`. A lingering
`<unknown>` is normal during this warm-up; if it never resolves, confirm the
`ClusterTriggerAuthentication` and user-workload monitoring from the previous steps. Wait for the
target to become numeric before driving load:

[source,bash,role="execute",subs="attributes"]
----
oc get hpa keda-hpa-qwen25-05b-llmd-keda -n {project_name} -w
----
====

== Exercise 5: Drive load and observe scaling

Load goes through the MaaS gateway, so first mint an API key bound to the high-limit subscription
from Exercise 3, then discover the model's gateway path — the same flow as
xref:05-maas-governance.adoc[Module 5, Exercise 6], but selecting the `qwen25-05b-llmd` model.

. Mint an API key and resolve the model's gateway path:
+
[source,bash,role="execute"]
----
export CLUSTER_DOMAIN=$(oc get ingresses.config.openshift.io cluster -o jsonpath='{.spec.domain}')
export HOST="https://maas.${CLUSTER_DOMAIN}"
export API_KEY=$(curl -sSk -X POST "${HOST}/maas-api/v1/api-keys" \
  -H "Authorization: Bearer $(oc whoami -t)" \
  -H "Content-Type: application/json" \
  -d '{"name":"llmd-scale-key","expiresIn":"1h","subscription":"qwen25-05b-llmd-demo"}' | jq -r .key)
# The gateway/maas-api may still be warming up, so the first /models call can return a transient
# non-JSON body (jq errors with "Invalid numeric literal"). Retry until the llm-d model appears.
for attempt in $(seq 1 10); do
  MODEL_JSON=$(curl -sSk "${HOST}/maas-api/v1/models" -H "Authorization: Bearer ${API_KEY}")
  echo "$MODEL_JSON" | jq -e '[.data[]? | select(.url | test("qwen25-05b-llmd"))][0]' >/dev/null 2>&1 && break
  echo "llm-d model not in catalog yet (attempt ${attempt}); retrying..."; sleep 3
done
# Select the llm-d model by its gateway path (both qwen models share the id "qwen25-05b").
export MODEL_URL=$(echo "$MODEL_JSON" | jq -re '[.data[] | select(.url | test("qwen25-05b-llmd"))][0].url')
export MODEL_NAME=$(echo "$MODEL_JSON" | jq -re '[.data[] | select(.url | test("qwen25-05b-llmd"))][0].id')
export MODEL_PATH=$(echo "$MODEL_URL" | sed -E 's#^https?://[^/]+##')
echo "Model: $MODEL_NAME  ->  ${HOST}${MODEL_PATH}"
----

[NOTE]
====
*The first request after the model starts is slow — this is expected.* A freshly started (or
freshly scaled-up) vLLM replica has cold caches, so its *first* completion can take ~30 seconds and
may even hit the gateway's default 30s route timeout and return `504`/`500`. This is a one-time
warm-up, not a failure: once the engine is warm, completions return in ~2 seconds. If your first
call times out, simply run it again — subsequent requests (and the load loop below) are fast.
====

. Generate *sustained* concurrent load through the gateway to build queue depth. The generator holds
  a fixed number of requests in flight for the whole duration — that is what keeps
  `num_requests_waiting` above the `ScaledObject` threshold long enough for KEDA to react. With
  concurrency `16` against an engine that admits `--max-num-seqs=8`, at least 8 requests are always
  waiting. It is standard-library Python (no `pip install`), and reads `HOST`, `MODEL_PATH`,
  `MODEL_NAME`, and `API_KEY` from the environment you exported above. Start it in the background and
  tee its progress to a log:
+
[source,bash,role="execute",subs="attributes"]
----
python3 manifests/06-llmd/load/load-test.py -c 16 -d 300 > /tmp/llmd-load.log 2>&1 &
----
+
[NOTE]
====
A one-shot burst fires every request at
once and drains before the ~30s user-workload-monitoring scrape and 15s KEDA poll can observe the
queue — so the metric never crosses the threshold and nothing scales. The burst also _under-reports
tokens_: at a large `max_tokens` the completions run past the gateway's 30s route timeout and return
`504`/`500` with no `usage` body, so Limitador meters *0 tokens* for them even though each still
counts as an authorized request (this is the "many requests, 100% success, 0 tokens" you would see on
the dashboard). The generator instead sustains the queue and keeps `--max-tokens` small (`32`) so
completions finish under the timeout and their tokens are metered.

With `-c 16` against `--max-num-seqs=8`, roughly 8 requests stay queued, so the deployment scales to
2 replicas (`ceil(8 / threshold 5)`). To push toward `maxReplicaCount` (4), raise concurrency —
`-c 32` keeps ~24 waiting (`ceil(24 / 5) = 4`).
====

. Watch the HPA drive the replica count. As `num_requests_waiting` crosses the threshold, the HPA's
  `TARGETS` climbs above `5` and `REPLICAS` rises (to `2` at `-c 16`), then settles back to
  `minReplicaCount` (`1`) after the load stops and the 60s cooldown elapses. Watch the HPA and the
  Deployment together (tail `/tmp/llmd-load.log` in another terminal for the generator's
  `ok`/`throttled`/`other` tally):
+
[source,bash,role="execute",subs="attributes"]
----
oc get hpa keda-hpa-qwen25-05b-llmd-keda -n {project_name} -w
# or watch the Deployment's replica count directly:
oc get deploy qwen25-05b-llmd-kserve -n {project_name} -w
----

. Correlate the scale event with the metrics that drove it. In the {ocp} console under
  *Observe -> Metrics* ({metrics_console_url}), overlay the queue depth and KV-cache utilization
  with the replica count over the same time window:
+
[source,promql]
----
kserve_vllm:num_requests_waiting
----
+
[source,promql]
----
kserve_vllm:kv_cache_usage_perc
----
+
These are the same user-workload metrics KEDA reads from Thanos (enabled in
xref:05-maas-governance.adoc[Module 5, Exercise 3]); the replica count rises after
`num_requests_waiting` crosses the `ScaledObject` threshold.

. Because the traffic ran through the MaaS gateway, the load also shows up in the per-subscription
  token telemetry from xref:05-maas-governance.adoc[Module 5, Exercise 8] — no extra wiring. Run
  this against the llm-d subscription (`limited_calls` stays 0 here, since the high limit is never
  exceeded):
+
[source,promql]
----
increase(authorized_hits{subscription="qwen25-05b-llmd-demo"}[5m])
----

=== Verify

* The replica count increases under load (up to `maxReplicaCount`) and scales back down once the
  queue drains.
* You can point to the `kserve_vllm:num_requests_waiting` threshold crossing that triggered the
  scale-up.
* `authorized_hits{subscription="qwen25-05b-llmd-demo"}` is non-zero — the scaling traffic was
  governed and metered by MaaS, and the llm-d model now appears in the Module 5 telemetry panels.

== Exercise 6 (Reference): Workload Variant Autoscaler on GPU

On a GPU-enabled {rhoai} {rhoai_version} cluster, the *Workload Variant Autoscaler (WVA)* is the
recommended way to scale llm-d. It reads KV-cache utilization and queue depth and creates a KEDA
`ScaledObject` for you — the same engine you drove directly in Exercises 3–4.

WVA is *not runnable on this CPU build*: the `DataScienceCluster` here has no `spec.components.wva`
field, so the `VariantAutoscaling` CRD is never registered, and WVA targets accelerated hardware.
The manifests are kept as GPU guidance:

* `manifests/06-llmd/autoscaling/dsc-wva-patch.yaml` — enables WVA in the `DataScienceCluster`
  (`spec.components.wva.managementState: Managed`).
* `manifests/06-llmd/autoscaling/variantautoscaling.yaml` — a `VariantAutoscaling` CR, and (in
  comments) the preferred `LLMInferenceService.spec.scaling.wva.keda` form with a GPU
  `vllm-cuda-rhel9` image and an accelerator label.

On such a cluster the flow would be: enable WVA in the DSC → deploy the `LLMInferenceService` with
`spec.scaling.wva` (or apply a `VariantAutoscaling` CR) → WVA creates the `ScaledObject`
automatically. No `ScaledObject`, RBAC, or `ClusterTriggerAuthentication` are authored by hand.

* You installed the llm-d prerequisites and the Custom Metrics Autoscaler, and deployed an
  `LLMInferenceService` attached to the MaaS gateway.
* You published the model through MaaS with a dedicated high-limit subscription, then authorized
  KEDA against user-workload monitoring and scaled the deployment with a `ScaledObject` driven by
  vLLM queue depth — no GPU required.
* You drove load through the MaaS gateway, watched replicas scale, correlated the scale event with
  the `kserve_vllm` queue and KV-cache metrics *and* the per-subscription token telemetry that came
  for free, and saw how the Workload Variant Autoscaler delivers the same capability on GPU.
